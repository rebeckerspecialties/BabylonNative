# WebXR core

One specification-level implementation of WebXR, written in Rust, exposed two ways:

- **N-API** through BabylonNative's `NativeXr` plugin, whose C++ classes become thin glue
  over this crate's C ABI (the plugin keeps ARKit, ARCore and OpenXR as backends).
- **WIT / WASI** through the `webidl:webxr` package in `wit/`, generated from the same W3C
  WebIDL and consumed by the webgpu-caps host.

Both bindings therefore expose the same W3C surface (interfaces, enums, dictionaries,
feature descriptors) by construction, and the same objects for rendering: projection-layer
textures are referred to by the numeric handle ids the WebGPU render-pass command stream
already uses.

## Layout

- `idl/` the W3C WebIDL as published by `@webref/idl` (version in `WEBREF_VERSION`), plus
  `dom-prelude.idl` with the shells of the DOM, WebGL and Geometry types the WebXR specs import.
- `wit/webxr.wit` generated by `Tools/webxr-idl-gen`; do not edit by hand.
- `Rust/` the `babylon_webxr_core` crate: session lifecycle, frame scoping, reference spaces
  and rigid transforms, feature negotiation, and the `Backend` trait platform trackers implement.

## Regenerating the WIT

```sh
cargo run -p webxr-idl-gen -- Core/WebXr/idl Core/WebXr/wit/webxr.wit
```

## Tooling decision

`webidl2wit` (Bytecode Alliance wasi-gfx, Apache-2.0, 0.1.1) is the WebIDL to WIT front end.
It is the generator wasi-webgpu derives its WIT from, it parses the WebXR module set
(partial interfaces, mixins, dictionaries with defaults, enums, promises as futures, typed
arrays as resources) and it exposes `HandleUnsupported` and `ResourceInheritance` options.
`webidl2wit` only produces WIT; Rust host traits come from `wit-bindgen` on that WIT, which is
also how the WASI component side is built, so one generated WIT drives both bindings.

Alternatives considered: `wasm-bindgen-webidl`/`web-sys` generate Rust *callers* of browser
APIs, the opposite direction; `weedle` is only a parser; Servo's `webxr_api` crate (MPL-2.0,
now `components/shared/webxr` in servo/servo) is a hand-written device abstraction over
OpenXR, glwindow and headless backends with Servo-specific IPC types, usable as a design
reference for `Backend` but not as a dependency. `napi-rs` can expose the core to N-API
without hand-written glue: with its `dyn-symbols` default feature disabled it links against
the Node-API symbols BabylonNative's JsRuntimeHost provides statically, and the host calls
`napi_register_module_v1(env, exports)` itself instead of loading a module; it needs the
`napi7` feature level, which the JsRuntimeHost fork implements.

## Generator gaps found on the WebXR set (webidl2wit 0.1.1)

Running the converter over the vendored set shows where upstream work is needed; the
generator works around the first item and records the others as warnings:

- `callback` definitions are skipped while operations taking them are kept, which leaves
  dangling type names (`XRFrameRequestCallback` in `requestAnimationFrame`). The generator
  turns skipped callbacks into placeholder resources; frame pacing is modelled by the
  host's completion mechanism in both bindings, not by a callback.
- `partial dictionary` is skipped: the module init options (`XRSessionInit.domOverlay`,
  `XRSessionInit.depthSensing`) are lost and must be contributed upstream.
- `iterable<T>` is skipped on `XRInputSourceArray` and `XRHand`; `getter` operations are
  skipped (`XRHand.get`). Both need list/index accessors in the WIT.
- `partial interface mixin` is skipped (`GlobalEventHandlers`, `WebGLRenderingContextBase`);
  harmless for the native core, which has no DOM event surface.

Types the WebXR specifications import from other specifications are declared as empty shells
in `idl/dom-prelude.idl` so the set converts as a closed world. The generated package imports
`wasi:io/poll@0.2.0`, vendored under `wit/deps` for validation.

## Specification coverage targeted first

WebXR Device API, AR module, Layers, WebGPU binding, depth sensing, lighting estimation,
hit test, anchors, raw camera access, hand input, plane detection, real-world meshing, DOM
overlays, gamepads module (all vendored in `idl/`).
